## Fix 1 — Menu bar: collapse to single row

**Symptom:** The new `.menu-bar` (sort, rated filter, fav filter, view toggle) renders as a
separate row *above* the existing `.browse-controls` row (status pills + secondary filters).
Two rows instead of one unified bar.

**Root cause:** `index.html` has `.menu-bar` as a standalone block, then `.browse-controls`
inside `#browseView` separately. They were never merged.

**Fix — `frontend/index.html` + `frontend/css/style.css` + `frontend/js/app.js`:**

Move the `.status-pills` group (`All / Unread / Reading / Read` buttons) out of
`.browse-controls` and into the site header `<div class="container inner">`, placed
immediately after `#searchWrap`. Reduce `#searchInput` max-width to make room (current
value is fine for the full-width it occupies now; shorten it so the pills fit alongside).

The `.menu-bar` block stays where it is below the header — it holds sort, rated, fav,
and view toggle, which belong there.

`.browse-controls` keeps the secondary filter dropdowns (genre, format, decade, year,
publisher, rating, b&w, group-by, count) — these are a secondary filter row, not the
primary navigation, so a second row for them is acceptable and expected.

The net result: header row = logo | surface tabs | search | **status pills** | gear | login.
Menu bar row = sort | dir | rated | fav | view toggle.
Secondary filters row = existing `.browse-controls` content (no pills).

JS: The pill click handlers and `activeStatus` state in `app.js` are unchanged in logic —
only the DOM location of the pill buttons moves. Confirm `document.querySelectorAll
('.status-pill')` still finds them after the move (it will, since the selector is
class-based not location-based).

CSS: Add pill styles to the header `.inner` flex context so they sit inline. Reduce
`search-input` max-width from its current value to ~180px on desktop so pills fit.
On narrower viewports the header already wraps — confirm pills wrap gracefully.

## Fix 2 — Multi-select: favourite toggle + rating clear

**Symptom:** The `★ Favorite` button in the selection toolbar is add-only — once a
card is favourited via multi-select, there is no way to unfavourite it from the toolbar.
Similarly, a star rating applied via multi-select cannot be removed.

**Root cause — `frontend/js/app.js`:**

`ensureSelectionToolbar()` hardwires the Favorite button to always call
`/progress/bulk/favorite` and `applyFavoriteToDom(ids, true)`. No unfavourite path exists.

**Fix A — favourite toggle:**

Change the `★ Favorite` button handler to inspect the current DOM state of selected
cards before deciding which endpoint to call:

```
if ALL selected cards have class .is-favorite
  → call POST /progress/bulk/unfavorite, applyFavoriteToDom(ids, false)
else
  → call POST /progress/bulk/favorite,   applyFavoriteToDom(ids, true)
```

Implement this check inside the button's click handler. The button label can stay
`★ Favorite` — the toggle behaviour is discoverable and consistent with the single-card
behaviour on the issue page (`app.js` line ~1775 already has this toggle pattern; follow
the same approach).

**Fix B — rating clear:**

Add a `✕` button (or a "Clear" label) at the start of the star rating row in the
toolbar, before the 1–5 stars. Clicking it calls `POST /progress/bulk/rate` with
`{ rating: 0 }` (or `null` — match what the single-issue rating endpoint accepts for
"no rating"). No DOM apply function needed — `exitSelectionMode()` fires after, and
the grid reflects the cleared state on next render. Alternatively, making a second
tap on the already-selected star clear it is acceptable if bulk rate can detect that
case — whichever is simpler given the existing `runBulkAction` plumbing.

## Fix 3 — Full Editor: Process All error → dismissible popup

**Symptom:** When Process All fires and validation fails on un-checked required fields
(genre/format/age-rating on target files), the error block written to `#feError` is an
enormous pipe-delimited string repeating the same three validation messages for every
file. It also persists until a manual page refresh.

**Root cause — `frontend/js/editor_full.js` line ~357:**

```js
showError(`Processed ${result.processed}. Errors: ${result.errors.join(' | ')}`);
```

`showError()` writes to the inline `#feError` div (no dismiss mechanism, no length cap).

**Fix — `editor_full.js` + `editor_full.html`:**

1. Add a small modal overlay to `editor_full.html` for process errors — distinct from
   the existing `#feError` inline div, which stays for short single-line errors
   (network errors, "select a file first", etc.). The modal needs: a title, a content
   area, and a close/dismiss button. Style it consistently with the log viewer modal
   already in `admin.html`.

2. In the Process All result handler, when `result.errors.length > 0`, instead of
   calling `showError()`, open this modal with:
   - Title: `Process All — Errors`
   - Body: summary line (`Processed X of Y files.`) followed by the first file's
     errors in full, then if there are more: `(N more files have the same errors —
     unchecked required fields default to blank and will fail validation. Tick Genre,
     Format, and Age Rating in the "Apply to All" column, or leave these files unselected.)`
   - A single **Dismiss** button that closes the modal.

3. `showError()` / `clearError()` / `#feError` are unchanged — still used for the
   short single-line cases.

## Fix 4 — Auth: library page triggers login popup

**Symptom:** Navigating back to the library (`/`) while password protection is on
triggers the admin login popup, even though the library requires no authentication.

**Root cause — `frontend/js/auth.js` `checkAuthStatus()`:**

```js
if (status.protection_enabled && !status.authenticated) {
  showLoginPopup();
}
```

`auth.js` is included on every page and `checkAuthStatus()` fires on `DOMContentLoaded`
everywhere — so the popup shows on `/` even though nothing on the library page is gated.

**Fix — `auth.js`:**

Gate the auto-popup on page path. Before calling `showLoginPopup()` inside
`checkAuthStatus()`, check `window.location.pathname`:

```js
const protectedPaths = ['/admin', '/editor'];
const onProtectedPage = protectedPaths.some(p => window.location.pathname.startsWith(p));
if (status.protection_enabled && !status.authenticated && onProtectedPage) {
  showLoginPopup();
}
```

The 401-interception path (`installFetchInterceptor`) stays unchanged — any
authenticated API call that bounces with 401 still surfaces the popup regardless of page.
That covers the Basic Editor popup on `/issue/{id}` (the fetch for the edit action
returns 401, which triggers the popup at that point, not on page load).

## Fix 5 — Auth: Login/Logout button always visible, text reflects state

**Symptom (two linked issues):**
- With require-password on, clicking Logout triggers the login popup before logging out
  (because `location.reload()` after logout runs `checkAuthStatus()` → popup fires).
- There is no way to log back in after logging out without turning require-password off,
  because the Logout button disappears when unauthenticated (so there's no "Login" trigger
  other than navigating to `/admin` directly).

**Root cause — `auth.js` `checkAuthStatus()`:**

```js
if (logoutBtn) logoutBtn.hidden = !status.authenticated;
```

Button is hidden when logged out. Logout handler does `location.reload()` which re-runs
`checkAuthStatus()` → on the library page after Fix 4 this no longer pops the modal, but
the button disappears and there's no Login affordance.

**Fix — `auth.js` + `index.html` (and `admin.html`, `editor_full.html`, etc.):**

1. Rename `#logoutBtn` → `#authBtn` in HTML and JS (or keep the id but change the label
   dynamically — either approach is fine; dynamic label is simpler if the element already
   exists everywhere).

2. In `checkAuthStatus()`, always show the button; set its label based on state:
   ```js
   authBtn.hidden = false;
   authBtn.textContent = status.authenticated ? 'Logout' : 'Login';
   ```
   Also store `status.authenticated` on the button as a data attribute so the click
   handler can branch without a re-fetch.

3. In `wireLogoutButton()` (rename `wireAuthButton()`), the click handler branches:
   ```js
   if (btn.dataset.authenticated === 'true') {
     // existing logout path
     await fetch('/api/admin/logout', { method: 'POST' });
     location.reload();
   } else {
     showLoginPopup();
   }
   ```

4. After `showLoginPopup()` succeeds (i.e., `onLoginSubmit` gets a 200), `location.reload()`
   already fires — so the button will re-render with the correct "Logout" label. No extra
   wiring needed.

**Note:** With Fix 4 in place, `location.reload()` after logout on the library page no
longer triggers the modal. The button showing "Login" gives the user a clear re-entry
point. On `/admin` or `/editor`, the existing auto-popup on reload handles re-auth.

## Fix 6 — Auth: disabling require-password must confirm current password

**Symptom:** An authenticated admin can deselect "Require Password" in Advanced Settings
with no credential re-entry — no confirmation that the person at the keyboard is the same
person who set the password.

**Current flow:** Unchecking the toggle → `PATCH /api/admin/settings` with
`{ password_protection: false }` → protection disabled.

**Fix — `frontend/js/admin.js` + `backend/routers/admin_auth.py`:**

**Frontend:** When the user unchecks the Require Password toggle, instead of immediately
saving, show a small inline confirmation area (below the toggle, not a separate modal —
keeps it close to the control being changed):
- Label: `Enter current password to disable protection:`
- Password input + Confirm button + Cancel button.
- Cancel restores the checkbox to checked without saving.
- Confirm POSTs `{ password_protection: false, current_password: "<value>" }`.

**Backend (`admin_auth.py` or `admin.py` settings endpoint):** When
`password_protection: false` is received, verify `current_password` against the stored
hash before disabling. Return `403` if it doesn't match. On success:
- Disable protection (clear enforcement flag).
- Force-disable Remote Administration in the same operation (per `ADMIN_SPEC.md §7.1.1`).
- Do NOT auto-logout the current session here — the user is already authenticated and
  confirmed their identity; they can choose to logout separately via the auth button.

## Fix 7 — Admin: Last Scan card shows "Never" after server restart

**Symptom:** The Last Scan card displays "Never" after a server restart, even when
`logs/last_scan_log.md` has a full history of past scans. Auto scan and scan-on-launch
results are also unverifiable for the same reason.

**Root cause:** `renderScanSection()` in `admin.js` uses `scanState.finished_at`, which
comes from the in-memory `ScanProgress` object in `scanner.py`. This resets to `None`
on every server restart.

**Fix — `backend/scan_logs.py` + `backend/routers/admin.py` + `frontend/js/admin.js`:**

**`scan_logs.py`:** Add a helper that reads the last line of `last_scan_log.md` and
returns the timestamp string from it (format: `DD/MM/YYYY HH:MM — Duration: ...`).
Return `None` if the file doesn't exist or is empty.

```python
def read_last_scan_timestamp() -> str | None:
    path = log_path("last_scan")
    if not path.exists():
        return None
    with open(path, "r", encoding="utf-8") as f:
        lines = [l.strip() for l in f if l.strip()]
    return lines[-1] if lines else None
```

**`backend/routers/admin.py`:** In the admin data endpoint (the one that returns
`scan_state`), include `last_scan_persisted` from the log:

```python
from backend.scan_logs import read_last_scan_timestamp
...
"scan_state": {
    "running": sp.running,
    "finished_at": ...,          # in-memory, None after restart
    "last_scan_persisted": read_last_scan_timestamp(),  # from log file
    ...
}
```

**`admin.js` `renderScanSection()`:** Prefer `finished_at` (live, gives duration context);
fall back to `last_scan_persisted` (from log); then `'Never'`:

```js
const lastScan = scanState.finished_at
  ? new Date(scanState.finished_at).toLocaleString()
  : (scanState.last_scan_persisted || 'Never');
```

The log entry format (`DD/MM/YYYY HH:MM — Duration: HH:MM:SS`) is already
human-readable, so displaying it directly when falling back from the log is fine — no
date parsing needed.

## Fix 8 — Admin: changed files log — distinguish change type

**Symptom:** The Changed Files log always shows "metadata updated" regardless of whether
the change was to the XML metadata, the archive contents (pages added/removed), or
something else.

**Root cause — `scan_logs.py` `append_changed_files_entry()`:**
The scanner detects "changed" purely by mtime delta and passes no change-type information
to the log function. The log entry format in `ADMIN_SPEC.md §8` only specifies
`"metadata updated"` because that was what Code could safely determine at build time.

**Fix — `backend/scanner.py` + `backend/scan_logs.py`:**

Extend the scan to detect change type before writing the log entry.

In `scanner.py`, when a file is flagged as changed (mtime delta ≥ 1s), compare the
current page count from the zip against the value stored in the DB
(`issue.page_count`). If different → `"archive changed (pages: {old} → {new})"`.
If page count is the same → `"metadata updated"`.

Pass a `change_type: str` argument through to `append_changed_files_entry()`:

```python
# scan_logs.py
def append_changed_files_entry(filename: str, change_type: str = "metadata updated") -> None:
    append_log_line("changed_files", f"{filename} — {change_type}")
```

```python
# scanner.py — in the changed-file handling block
old_page_count = existing_issue.page_count
new_page_count = count_pages_in_zip(filepath)   # use existing zip-read utility
change_type = (
    f"archive changed (pages: {old_page_count} → {new_page_count})"
    if new_page_count != old_page_count
    else "metadata updated"
)
append_changed_files_entry(filename, change_type)
```

Check what zip-reading utility already exists in `scanner.py` before adding anything new —
it already reads the zip for XML extraction, so page-counting should reuse that open.
Don't open the zip twice.

**Note:** Filename changes are already handled as separate new-row insert + missing-flag
on the old row (confirmed in `ADMIN_SPEC.md §8`). They do not produce a "changed" entry,
so no change is needed there.

## Fix 9 — Admin: scheduled backup — add last-backup indicator + surface failures

**Symptom:** Backup was set to 1hr / destination `D:\` and no backup appeared after 2
hours. No in-app feedback that a backup ran (or failed).

**Investigation notes:**
- Scheduler logic looks correct: `'1hr'` key maps to `3600` in `_BACKUP_FREQUENCY_SECONDS`
  and the poll loop fires every 60s, so the trigger should occur at the 60-minute mark.
- `run_database_backup()` silently swallows `FileNotFoundError` and `OSError` —
  if the DB path or destination is wrong, there is no visible error.
- The current config has `backup_folder: "D:/"` and `db_path: "backend/comicvault_v2.db"`,
  both correct. Backup file would land at `D:\comicvault_backup_TIMESTAMP.db`.
- Most likely cause: server was restarted after setting the frequency, resetting
  `elapsed = 0` in `backup_loop`. The 2-hour window may not have included a continuous
  60-minute run.

**Fix — two parts:**

**Part A — store and display last backup timestamp:**

In `run_database_backup()` (`backend/routers/admin.py`), after a successful copy,
write the timestamp to `config.json`:

```python
from backend.config import update_config
update_config({"last_backup_at": datetime.now().isoformat()})
```

In the admin data endpoint, include `last_backup_at` from config in the response.

In `admin.js`, add a "Last Backup" display near the Backup Database button (top action
row or the scheduled backup settings block — wherever makes visual sense). Format it
like Last Scan: localised datetime string, or `'Never'` if not set.

**Part B — surface scheduler failures:**

In `_run_backup_background()` (`scheduler.py`), update the `except` blocks to also
write to a `backup_error` key in config, so the admin page can show a warning badge
if the last scheduled backup attempt failed:

```python
except FileNotFoundError:
    logger.error("Scheduled backup skipped — database file not found")
    update_config({"last_backup_error": "Database file not found"})
except OSError as e:
    logger.exception("Scheduled backup failed")
    update_config({"last_backup_error": str(e)})
```

Clear `last_backup_error` on a successful backup. Show the error string in the admin UI
near the Last Backup indicator if it is set.
